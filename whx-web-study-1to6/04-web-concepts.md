## 1. 协议：HTTP / HTTPS

**HTTP（HyperText Transfer Protocol）** 是浏览器和服务器之间"对话的语言"：浏览器发出一个"请求"，服务器返回一个"响应"。所有网页、图片、接口数据，背后都是 HTTP 在搬运。

### 1.1 一次 HTTP 请求发生了什么？

以在浏览器地址栏输入 `https://example.com` 为例：

```
┌──────────┐                                ┌──────────┐
│  浏览器  │                                │  服务器  │
└────┬─────┘                                └────┬─────┘
     │ ① DNS 解析：example.com → 93.184.216.34   │
     │ ────────────────────────────────────────►  │
     │ ② TCP 三次握手（HTTP/3 跳过）             │
     │ ◄──────────────────────────────────────►  │
     │ ③ TLS 握手（HTTPS 时）                    │
     │ ◄──────────────────────────────────────►  │
     │ ④ 发送 HTTP 请求报文                      │
     │ ────────────────────────────────────────►  │
     │            GET / HTTP/1.1                 │
     │            Host: example.com              │
     │            User-Agent: Chrome/...         │
     │            Accept: text/html              │
     │ ⑤ 服务器返回 HTTP 响应                    │
     │ ◄──────────────────────────────────────── │
     │            HTTP/1.1 200 OK                │
     │            Content-Type: text/html         │
     │            ...                           │
     │            <html>...</html>              │
     │ ⑥ 解析 HTML → 继续请求 CSS/JS/图片       │
     │ ────────────────────────────────────────►  │
     │ ◄──────────────────────────────────────── │
     │ ⑦ 拼出最终页面                            │
```

### 1.2 常见状态码速查

| 状态码 | 含义 | 什么时候遇到 |
| --- | --- | --- |
| `200` | OK | 一切正常 |
| `301` | 永久重定向 | 网站换域名 |
| `302` | 临时重定向 | 临时跳转 |
| `304` | Not Modified | 命中缓存 |
| `400` | 请求参数错误 | 前端传参格式不对 |
| `401` | 未登录 / Token 失效 | 需要鉴权的接口 |
| `403` | 无权限 | 登录了但没有访问该资源的权限 |
| `404` | 资源不存在 | URL 写错、资源被删 |
| `500` | 服务器内部错误 | 后端代码崩了 |
| `503` | 服务暂不可用 | 服务器过载或维护中 |

> 记忆口诀：**2 开头都挺好，3 开头转一转，4 开头前端错，5 开头后端错**。

### 1.3 HTTP 各版本对比

| 版本 | 底层传输 | 主要特点 | 默认端口 | 当前占比 |
| --- | --- | --- | --- | --- |
| **HTTP/1.0** | TCP | 每个请求都要新建连接 | 80 | 几乎绝迹 |
| **HTTP/1.1** | TCP | **长连接**、流水线，但有"队头阻塞" | 80 | 仍占一定比例 |
| **HTTP/2** | TCP + TLS | **多路复用**（一个连接并发多个请求）、二进制分帧、头部压缩 | 443 | 主流 |
| **HTTP/3** | **QUIC（基于 UDP）** | 彻底解决队头阻塞、连接建立更快、移动网络更稳 | 443 | 快速普及中 |

> 简单记：
> - **HTTP/1.1**：一次只能发一个，等回来再发下一个（想象只有一条收银台通道的超市）；
> - **HTTP/2**：一条连接上**同时跑**多个请求（开了多个收银台）；
> - **HTTP/3**：底层从 TCP 换成 UDP 的 **QUIC**，进一步减少等待，移动网络切换 Wi-Fi 时也不会断。

### 1.4 HTTPS 是什么？

HTTPS = HTTP + TLS（早期叫 SSL）。它在 HTTP 之上加了两件事：

- **加密**：第三方无法偷听内容；
- **身份验证**：通过证书确认"你访问的 example.com 真的是 example.com"，防钓鱼。

> 现在浏览器地址栏出现"不安全"提示的页面，几乎都是 HTTP 的。**新项目请一律使用 HTTPS**。

本地开发时常用自签名证书，浏览器会提示"不安全"，属于正常现象。

### 1.5 几个前端常用的请求方法

| 方法 | 用途 | 幂等性 | 典型场景 |
| --- | --- | --- | --- |
| `GET` | 读取资源 | 幂等 | 列表、详情 |
| `POST` | 新建资源 / 提交数据 | 非幂等 | 注册、登录、提交表单 |
| `PUT` | 整体替换资源 | 幂等 | 整体更新 |
| `PATCH` | 局部更新资源 | 非幂等 | 修改昵称、修改密码 |
| `DELETE` | 删除资源 | 幂等 | 删除文章、注销账号 |
| `OPTIONS` | 预检请求 | 幂等 | 跨域复杂请求前的探测 |

> 幂等 = 同样的请求执行一次和执行 N 次结果一致。`GET` 多次读不变，`DELETE` 删一次和删十次效果一样；`POST` 每提交一次都会新建一条记录。

### 1.6 请求报文与响应报文长什么样？

用 DevTools 的 Network 面板抓一个请求，可以直观看到：

**Request Headers**（请求头）
```
GET /api/users?page=1 HTTP/1.1
Host: api.example.com
User-Agent: Mozilla/5.0 ...
Accept: application/json
Authorization: Bearer eyJhbGciOi...
Cookie: sid=abc123
```

**Response Headers**（响应头）
```
HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8
Cache-Control: max-age=60
Set-Cookie: token=xxx; HttpOnly
```

**Response Body**（响应体）
```json
{
  "code": 0,
  "data": [
    { "id": 1, "name": "Tom" },
    { "id": 2, "name": "Jerry" }
  ]
}
```

## 2. 网页、网站、静态与动态

这几个词天天在用，但常被混着说。厘清它们的区别，能帮你理解后续的"前端渲染 vs 后端渲染"。

### 2.1 基本概念

| 名称 | 定义 | 举例 |
| --- | --- | --- |
| **网页（Web Page）** | 一份单独的 HTML 文档 | `https://example.com/about.html` |
| **网站（Website）** | 多个互相链接的网页的集合 | 知乎、淘宝、博客 |
| **静态网页** | 服务器原样返回 HTML，**内容在请求时已经固定** | 个人博客文章、文档站 |
| **动态网页** | 服务器在请求时**根据数据动态生成** HTML | 微博首页、股票行情、电商商品页 |

### 2.2 静态网站 vs 动态网站

| 维度 | 静态网站 | 动态网站 |
| --- | --- | --- |
| 内容是否变化 | 内容固定 | 内容随用户 / 时间 / 数据变化 |
| 是否需要数据库 | 通常不需要 | 通常需要 |
| 性能 | 极快，可以丢 CDN | 取决于后端实现 |
| 适用场景 | 文档、博客、宣传页、营销落地页 | 电商、社交、后台管理 |
| 典型技术 | Hugo、VuePress、Astro | PHP / Node.js / Java / Python 等 |

> 重点不是"哪个更好"，而是**场景决定选择**。一个公司官网用静态站足够；一个电商平台必须用动态站。

### 2.3 静态站也能"看起来"动态

随着 JamStack 思想流行，很多博客 / 文档站会选择：

- **构建时**把所有数据预渲染成 HTML（**SSG**，详见 [3.4](#34-ssg静态站点生成static-site-generation)）；
- 部署到 CDN（**内容分发网络**），全球访问都很快；
- 想要评论 / 搜索等"动态能力"时，再去调用第三方 API。

代表项目：**VitePress**、Astro、VuePress、Hexo、Hugo。

> 这一节只是个引子：到底什么叫 SSG、它和 SSR 的本质区别是什么、什么时候该用它——见 [第 3 章「单页应用、多页应用与渲染策略」](#3-单页应用多页应用与渲染策略)。

## 3. 单页应用、多页应用与渲染策略

这一节讲的"应用"，指的不是桌面软件，而是**一个完整的前端工程项目**。

> **这一节会回答一个核心问题**：当用户打开一个 URL 时，HTML 到底是在**谁的电脑**、**什么时间**、**怎么拼出来的**？答案不同，就对应不同的渲染策略。

### 3.0 一张总览：四大渲染策略

| 策略 | HTML 在哪拼 | 何时拼 | 一句话定位 |
| --- | --- | --- | --- |
| **MPA** | 服务器 | 每次请求 | 一座"老式别墅"，每进一个房间都要重新开门 |
| **CSR（SPA）** | 浏览器 | 每次首屏 | 一座"空壳精装房"，装修在租客入住后才开始 |
| **SSR** | 服务器 | 每次请求 | 一座"现房出租"的酒店，家具齐了，租客拎包入住后还会"装修" |
| **SSG** | **构建时** | 一次 | 一座"提前盖好的样板房"，所有房间都装修好，客人随时来 |
| **ISR / 流式 SSR** | 服务器 | 首次 / 按需 | 样板房 + 局部翻新，常住区域永久保留，偶尔改动的区域按需重拼 |

> **构建时** vs **请求时** 是 SSG 与 SSR 最大的区别：SSG 是在你 `npm run build` 那一刻就把所有页面拼成 HTML 文件；SSR 是用户每次访问都实时拼。

### 3.1 MPA（多页应用，Multi-Page Application）

**传统形态**：每个 URL 对应一个完整的 HTML 文件，每次跳转页面 = 浏览器发一次新请求 = 整页刷新。

```
浏览器                   服务器
  │  GET /index.html       │
  │ ────────────────────► │  返回首页 HTML
  │ ◄──────────────────── │
  │  GET /about.html       │
  │ ────────────────────► │  整页刷新，返回 about HTML
  │ ◄──────────────────── │
```

- 优点：SEO 友好、对老浏览器友好；
- 缺点：页面之间切换慢、用户操作被打断；
- 典型技术：服务端模板渲染（PHP、Jinja、Thymeleaf ……）。

### 3.2 SPA（单页应用，Single-Page Application）

**现代主流**：整个项目**只有一个 HTML 文件**（通常叫 `index.html`），页面之间的切换由前端 JS 在浏览器内完成（通过改变 URL 路径 + 局部更新 DOM），**不会再向服务器请求新页面**。

```
浏览器                          服务器
  │  GET /index.html (首次)        │
  │ ────────────────────────────► │  返回空壳 + JS 入口
  │ ◄──────────────────────────── │
  │  GET /api/users (数据接口)     │
  │ ────────────────────────────► │
  │ ◄──────────────────────────── │
  │  浏览器内 JS 切到 /about        │
  │  (只更新 DOM，URL 变了，HTML 没换)
```

- 优点：切换快、交互流畅、前后端解耦；
- 缺点：首屏慢、对 SEO 不友好（爬虫看到的只是一个空壳 HTML）；
- 典型技术：**Vue 3 + Vue Router**、React + React Router、SvelteKit 等。

#### 什么时候选 SPA？

- 后台管理系统、看板、工具型产品（如 Notion、Figma）—— 不在乎 SEO、追求极致交互；
- 重交互、重表单、重实时刷新的产品；
- 团队已经熟悉 Vue/React 等框架。

### 3.3 SSR（服务端渲染，Server-Side Rendering）

**思想**：让服务器先把 HTML **"渲染"** 好再发给浏览器。浏览器拿到的不是空壳，而是**已经填好数据的完整 HTML**，用户能立刻看到内容；随后浏览器再"接管"（hydration）变成可交互的 SPA。

```
浏览器                          服务器
  │  GET /article/123              │
  │ ────────────────────────────► │
  │   服务端：拿数据 → 拼 HTML       │
  │ ◄──────────────────────────── │  ← 返回已填好内容的 HTML
  │  浏览器：渲染出页面              │
  │  浏览器：下载 JS，hydration    │  ← 变成可交互的 SPA
```

**适用场景**：

- 强 SEO 场景：电商商品页、内容站点、新闻门户；
- 首屏性能要求极高：移动弱网、SEO 收录是命脉；
- 兼顾"既要 SPA 的体验、又要静态首屏的 SEO"。

**典型框架**：Vue 生态的 **Nuxt 3**、React 生态的 **Next.js**。

### 3.4 SSG（静态站点生成，Static Site Generation）

**思想**：在**构建时**（`npm run build`）就把所有页面渲染成静态 HTML 文件，部署到 CDN，**用户访问时服务器不再做拼接**。

```
构建时（npm run build）                  用户访问时
┌──────────────────────┐         ┌──────────────────────┐
│ 读取所有 Markdown /  │         │ 浏览器访问 /article/1 │
│ 数据源 / 路由列表      │         │ ──────────────────► │
│ 遍历生成 HTML         │ ──────► │ CDN 直接返回已生成    │
│ 写到 dist/ 目录       │   部署   │ 的 HTML（不调任何后端）│
└──────────────────────┘         └──────────────────────┘
```

**与 SSR 看似相似，区别在于"何时拼"**：

| 维度 | SSR | SSG |
| --- | --- | --- |
| HTML 在何时生成 | **请求时**（每个用户来都拼一次） | **构建时**（只拼一次） |
| 服务器在运行时做什么 | 拿数据 + 拼 HTML + 返回 | **几乎不做事**（直接吐静态文件） |
| 首屏速度 | 快 | **最快** |
| 适用数据 | 高频变化的实时数据 | 内容相对稳定、可提前预知全部路径 |
| 部署目标 | 需要 Node 服务 | 任何静态服务器 / CDN |
| 成本 | 中等（按请求算） | **最低**（CDN 流量极便宜） |

**典型适用**：

- 博客、文档站、营销页、官网、作品集
- 内容更新频率不高（每天 / 每周）
- 想"零运维、零 Node、零成本"上线

**典型框架**：

- **VitePress**（Vue 生态，文档站首选）
- **Astro**（"内容驱动"，支持 Vue / React / Svelte 多框架混合）
- **Nuxt 3 `nuxt generate`** / **Next.js `next export`**
- 经典老牌：Hexo、Hugo、Jekyll

**一个最简的 SSG 流程示例（伪代码）**：

```js
// build.js —— 极简 SSG 思路示意
import fs from 'node:fs'
import { renderPage } from './renderer'

const posts = fs.readdirSync('./content')        // 读取所有文章
for (const file of posts) {
  const html = renderPage(file)                  // 拼成 HTML
  fs.writeFileSync(`./dist/posts/${file}.html`, html)
}
```

> 实际生产中用 VitePress / Astro 远比这个省事——它们已经帮你把"读 Markdown → 渲染 → 写文件 → 加路由"全做好了。

**SSG 的两个"软肋"**：

1. **内容更新要重新构建**：文章一改，就得 `npm run build` 一次。1000 篇文章时一次构建要好几分钟。
2. **不擅长"千人千面"**：无法根据登录用户显示不同内容——HTML 是同一份。

针对这两点，业界又演化出了 **ISR** 和 **流式 SSR**，见 3.5。

### 3.5 ISR 与流式 SSR：SSR 与 SSG 的混合形态

传统 SSR 的痛点是"每次请求都拼，浪费"；传统 SSG 的痛点是"内容一变就要全量重建"。**ISR / 流式 SSR** 想同时解决这两边。

#### ISR（Incremental Static Regeneration，增量静态再生）

- **首次**访问某页面 → 服务器渲染一次 → 缓存到 CDN；
- 之后 N 秒内的访问 → **全部直接返回缓存**；
- N 秒过期后 → 下一次访问时**后台**重新渲染一次（用户拿到的还是旧版本，但下次就是新的了）。

```
访问 1:  渲染 + 缓存
访问 2~N: 直接返回缓存
过期后访问 N+1: 仍然返回旧版（同时后台悄悄重渲染）
再下一次: 返回新版
```

代表：Next.js 的 `revalidate` 机制。

#### 流式 SSR（Streaming SSR）

传统 SSR 要等**整个页面**在服务器拼完才能返回；流式 SSR 是**边拼边吐**——服务器先把骨架 HTML 流式返回给浏览器，浏览器立刻开始渲染；中间需要数据的地方等数据来了再"塞进去"。

```html
<!-- 服务器流式返回的 HTML 片段（示意） -->
<header>...</header>
<main>
  <h1>{{ 文章标题 }}</h1>
  <!-- ↑ 先吐到这里，浏览器立刻渲染标题 -->
  <Suspense>
    <!-- ↑ 下面这块是异步组件，等数据 -->
    <CommentList />  <!-- 后台再吐 -->
  </Suspense>
</main>
```

> **好处**：TTFB（首字节时间）极短，用户立刻看到骨架；**代价**：实现复杂，需要框架支持（如 React 18+ 的 Server Components、Vue 3 的 Suspense）。

#### 三者速记

| 形态 | 一句话 |
| --- | --- |
| **SSG** | 提前把整栋楼盖好，客人随时来 |
| **ISR** | 提前盖好，但每 N 年"局部翻新"一次 |
| **流式 SSR** | 不盖整栋楼，一层一层往上盖，盖一层就开放一层 |

### 3.6 现代渲染策略总览

把上面 3.1–3.5 串起来看：

| 策略 | HTML 在哪拼 | 何时拼 | 服务器开销 | 首屏 | SEO | 典型场景 |
| --- | --- | --- | --- | --- | --- | --- |
| **MPA** | 服务端模板 | 每次请求 | 高 | 中 | 优 | 内容站、PHP 老项目 |
| **CSR（SPA）** | 浏览器 | 每次首屏 | 极低 | 慢 | 差 | 后台、看板、工具型 |
| **SSR** | Node 服务器 | 每次请求 | 高 | 快 | 优 | 强 SEO + 高频个性化 |
| **SSG** | 构建机器 | 一次 | **零** | **最快** | **最优** | 博客、文档、官网 |
| **ISR** | Node 服务器 | 首次 / 过期 | 中 | 快 | 优 | 内容站 + 偶尔更新 |
| **流式 SSR** | Node 服务器 | 流式 | 中 | **极快** | 优 | 复杂大页、慢接口 |

#### 选型决策树

```
你的内容是"千人千面"吗？
  ├─ 是（按用户/时间显示不同内容）
  │     └─ 走 SSR 或 流式 SSR（Nuxt 3 / Next.js）
  │
  └─ 否（所有人看到的内容一样）
        │
        内容更新频率？
          ├─ 几乎不变（一年改几次）
          │     └─ 选 SSG：博客、文档、官网 → VitePress / Astro
          │
          └─ 偶尔变（每天/每周）
                │
                单页面构建时长能否接受？
                  ├─ 能（几百篇以内）
                  │     └─ 仍选 SSG + 自动化部署
                  │
                  └─ 不能（几千篇 + 频繁更新）
                        └─ 选 ISR：Next.js / Nuxt 3 nitro prerender
```

> **经验法则**：
> - **80% 的"内容站"**其实只需要 SSG，便宜、快、好部署；
> - **真正的"业务系统"**才需要 SSR（SPA 顶多 5% 场景下要 SSR）；
> - **永远不要一上来就 SSR**——SSR 比 SSG / SPA 复杂得多，只有收益明显时才值得。

### 3.7 给小白的"先学哪个"清单

| 你的身份 | 推荐路径 |
| --- | --- |
| 零基础 / 转行 | CSR（SPA） → SSG → SSR → 流式 |
| 做博客 / 文档 | 直接学 **VitePress / Astro**（SSG 路线） |
| 想做内容 + 简单交互 | SSG + 局部 CSR（典型：博客评论区用 JS 拉接口） |
| 找工作 / 面试 | 重点学 **SSR（Nuxt 3）+ SSG**，理解 hydration |
| 公司已经有 SSR 项目 | 先看懂**改造前的 CSR**，再读**改造后的 SSR**，不要倒着来 |

## 4. 浏览器渲染流水线（简版）

理解浏览器"怎么把 HTML 变成像素"，能帮你理解很多性能优化的依据。

```
HTML 文本
   │
   ▼
① 解析 HTML → 生成 DOM 树
   │
   ▼
② 解析 CSS → 生成 CSSOM 树
   │
   ▼
③ 合并 DOM + CSSOM → 渲染树（Render Tree）
   │  （只包含可见元素）
   ▼
④ 布局（Layout / Reflow）→ 计算每个节点的位置和大小
   │
   ▼
⑤ 绘制（Paint）→ 把像素画到屏幕
   │
   ▼
⑥ 合成（Composite）→ 把不同图层合并输出
```

### 4.1 三个优化关键词

| 词 | 含义 | 怎么优化 |
| --- | --- | --- |
| **重排（Reflow）** | 重新计算布局 | 减少一次性修改大量 DOM |
| **重绘（Repaint）** | 重新绘制像素 | 用 transform / opacity 替代 top / left |
| **合成（Composite）** | 图层合并 | 用 `will-change` 提示浏览器提升图层 |

> 经验法则：能改 `transform` 就不改 `top`；能改 `opacity` 就不改 `display`。

### 4.2 关键渲染路径

从输入 URL 到看到第一帧画面，浏览器要：

1. 下载 HTML → 解析；
2. 遇到 `<link rel="stylesheet">` **同步阻塞**地下载 CSS（渲染要等）；
3. 遇到 `<script>`（无 async/defer）**同步阻塞**地下载并执行（渲染要等）；
4. 解析出 DOM 后开始渲染。

> 一句话：**CSS 放 `<head>`，JS 放 `<body>` 底部或加 `defer`**，是最朴素也最有效的优化。
